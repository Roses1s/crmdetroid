# CRM «Детроид»

CRM для логистической компании: канбан лидов, карточка лида с логом и вложениями,
заявки с маржой, общий справочник направлений и перевозчиков, управление сотрудниками.

**Стек:** PHP 8.1+ (`api.php` + `db.php`, без фреймворков) и MySQL 8. Фронт — чистый JS без сборки.
Хостинг — SpaceWeb (Apache, `.htaccess`).

## Файлы

| Файл | Назначение |
|---|---|
| `index.html`, `app.css`, `noscript.css`, `js/` | Фронт. `ui.html` — разметка приложения, отдаётся только после входа |
| `api.php` | Все действия API: `api.php?action=…` |
| `db.php` | Подключение к MySQL, миграции схемы, SQL-хелперы |
| `config.php` | **Не в git.** Доступы к БД. Создаётся из `config.example.php` |
| `schema.sql` | Справочная копия схемы (совпадает с миграциями в `db.php`) |
| `uploads/` | Вложения из логов. Закрыт для веба, файлы отдаёт `api.php?action=file` |
| `data/` | Секрет для login-CSRF (`data/.csrf_secret`, права 0600) и файлы PHP-сессий (`data/sessions/`), создаётся сам |
| `tests/` | Регрессионные проверки для тестового стенда (см. «Тесты»). На прод не заливать |

## Установка на SpaceWeb

1. Панель [cp.sweb.ru](https://cp.sweb.ru/main/) → **Базы данных** → **Создать**, тип **MySQL 8**.
   Запомните имя БД, логин и пароль.
2. Скопируйте `config.example.php` → `config.php` и впишите доступы:

   ```php
   define('CRM_DB_HOST', '127.0.0.1');   // MySQL 8 на SpaceWeb, не localhost
   define('CRM_DB_PORT', '3308');
   define('CRM_DB_NAME', 'uXXXX_crm');   // имя из панели
   define('CRM_DB_USER', 'uXXXX_crm');   // логин из панели
   define('CRM_DB_PASS', 'пароль_mysql');
   ```

3. Залейте файлы репозитория и ваш `config.php` в `public_html`.
   Таблицы создадутся **сами** при первом запросе к `api.php`; импорт `schema.sql` не нужен.
4. Первый вход: `admin@detroid.local` / `admin123`. CRM сразу потребует задать свой пароль (8–64 символа).

**Обновление работающего сайта:** заливайте `api.php`, `db.php`, `index.html`, `ui.html`, `app.css`,
`noscript.css`, `icon.svg`, `js/`, `.htaccess` (и при необходимости `uploads/.htaccess`, `data/.htaccess`).
**Не перезаписывайте** живой `config.php` и содержимое `uploads/`, `data/`.

Миграции схемы выполняются автоматически первым запросом после обновления (под блокировкой
`GET_LOCK('crm_migrate')`, поэтому одновременные первые запросы друг другу не мешают). Учётной записи
MySQL нужны права на `ALTER`/`CREATE`. **Перед обновлением снимите дамп БД** (панель SpaceWeb →
phpMyAdmin → Экспорт): миграции необратимы.

Что делает текущая версия схемы (v12) с существующими данными:
- ставка и маржа заявок переводятся из текста в `DECIMAL(15,2)`; исходные строки сохраняются в
  `rate_raw` / `margin_raw`. В число попадают только однозначные суммы («45 000», «45000 руб.», «17608,65»);
  диапазоны и текст («12000-15000», «от 40 000», «1e5») в числе становятся пустыми, но остаются в `*_raw` —
  их можно найти запросом `SELECT * FROM crm_lead_apps WHERE rate IS NULL AND rate_raw <> ''` и поправить руками;
- добавляются индексы `crm_leads(user_id, stage)` и `(user_id, inn)`, убирается бесполезный `idx_stage`;
- добавляется колонка `token_version` в `crm_users` (счётчик инвалидации сессий при смене роли;
  существующие данные не затрагиваются, значение по умолчанию 0).

## Лимиты на вход и IP клиента

Защита от перебора считает попытки входа по IP (`REMOTE_ADDR`). Если PHP на хостинге стоит за
прокси (nginx перед Apache) и все запросы приходят с одного внутреннего адреса — весь офис будет
делить один лимит. Проверка: откройте в браузере `api.php?action=whoami` — если `ip` не ваш внешний,
а что-то вроде `127.0.0.1` / `10.x`, впишите этот адрес в `config.php`:

```php
define('CRM_TRUSTED_PROXIES', '127.0.0.1, 10.0.0.0/8');
```

После этого IP клиента берётся из `X-Forwarded-For` / `X-Real-IP`, но **только** когда запрос
пришёл с перечисленного прокси — подделать адрес снаружи нельзя. Пустой список = заголовкам не верить.

## Локальный запуск

Нужен PHP 8.1+ с `pdo_mysql` и `mbstring`, и MySQL/MariaDB. Создайте `config.php` и запустите
из корня репозитория:

```
php -S 0.0.0.0:8080
```

## Тесты

Оба набора работают против **тестового** стенда (создают пользователей и лиды — на проде не запускать):

```
# API: права, вложения, поиск, передача лидов, пароли, миграционные инварианты
CRM_URL=http://127.0.0.1:8080 ADMIN_PASS='пароль_админа' bash tests/api-smoke.sh

# Клиентская логика js/app.js в jsdom (нужен `npm i jsdom`; ожидает сотрудников
# ivan@x.ru / IvanPass123 и «Пётр Сидоров» в тестовой БД)
CRM_URL=http://127.0.0.1:8080 ADMIN_PASS='пароль_админа' NODE_PATH=./node_modules node tests/e2e-jsdom.mjs
```

## Таблицы

|---|---|
| `crm_users` | сотрудники, bcrypt-пароли, роль `admin`/`user` |
| `crm_stages` | колонки канбана **своего** аккаунта |

## Права и правила (кто что может)

| Действие | Кто |
|---|---|
| Лиды, этапы, заявки, лог лида | владелец доски; админ — на любой доске через `?as=ID` |
| Передать лид другому сотруднику | владелец доски (и админ с его доски): в поле «Продавец» выбрать сотрудника из подсказки **полным именем** и подтвердить. Одна фамилия лид не переводит. В лог получателя пишется системная запись |
| Системные записи лога («Лид создан», «Лид передан», «Статус изменён») | удалять может только админ — это след истории карточки |
| Записи лога уволенных сотрудников | правит/удаляет только админ (совпадение имени с новым сотрудником прав не даёт) |
| Справочник направлений/перевозчиков: добавить, вести лог | все сотрудники |
| Справочник: переименовать/удалить направление или перевозчика (каскадно удаляются чужие записи и файлы) | тот, кто добавил, или админ |
| Пересечения в поиске (чужие лиды с тем же клиентом) | показываются только по запросу от 4 символов названия или 4 цифр ИНН, не более 20 |
| Список коллег (имена) | виден всем сотрудникам — нужен для передачи лидов; e-mail и роли видит только админ |
| Сотрудники, `api.php?action=whoami`, `sweep_uploads` (уборка файлов без записей в БД) | админ |

Пароли: 8–64 символа (считаются символы, не байты). После смены пароля — своего или админом —
все остальные сессии этого пользователя закрываются. При смене роли (admin → user / user → admin)
сессии тоже закрываются: `token_version` инкрементируется, и отпечаток в сессии перестаёт совпадать.

Вложения в логах (`.doc/.docx/.xls/.xlsx/.ppt/.pptx/.csv/.zip/.7z`) CRM хранит как есть и не проверяет
на макросы — это файлы, которыми обмениваются свои сотрудники. Открывать чужие офисные документы
из лога стоит с теми же предосторожностями, что и из почты (защищённый просмотр, без включения макросов).

## Удаление сотрудника

Лиды привязаны к сотруднику. При удалении CRM показывает, сколько у него лидов, и предлагает
передать их другому сотруднику (по умолчанию — вам): лог, вложения и заявки сохраняются,
этап остаётся, если такой есть у получателя, в лог каждого лида пишется запись о передаче.
Вариант «Удалить безвозвратно» стирает лиды вместе с логами, файлами и заявками — отменить нельзя.

## Безопасность (кратко)

- Сессии в cookie `HttpOnly`/`SameSite=Lax`/`Secure` (на HTTPS): 8 часов без активности или 14 дней
  с момента входа — затем вход заново (открытая вкладка сессию бесконечно не продлевает). Файлы сессий
  хранятся в своём каталоге `data/sessions/`, чтобы сборщик мусора общего каталога хостинга их не удалял.
- Все изменяющие действия — только `POST` с заголовком `X-CSRF-Token`; чтение — `GET`.
- Форма входа защищена одноразовым HMAC-токеном (ключ в `data/.csrf_secret`; если каталог `data/`
  недоступен на запись, вход не работает и в логе сервера есть сообщение — дайте права на запись).
  Лимиты: 8 попыток на пару e-mail+IP и 80 на IP за 15 минут; успешный вход сбрасывает счётчик только
  своей пары e-mail+IP. За офисным NAT весь офис делит лимит IP — см. `CRM_TRUSTED_PROXIES` выше.
- Загрузка файлов: белый список расширений, проверка сигнатуры, ≤5 МБ, ≤8 файлов на запись, имя
  обрезается до 200 символов; каталог `uploads/` снаружи закрыт, выдача — через `api.php?action=file`
  с проверкой прав. Файлы без записей в БД удаляются автоматически (раз в ~1000 запросов) или
  по `POST api.php?action=sweep_uploads` (админ).
- Предупреждения PHP не попадают в ответ: любая ошибка — JSON `{"success":false,"error":"Ошибка сервера"}`
  (HTTP 500) и запись в лог сервера (`error_log`) с действием и пользователем.
- `config.php`, `db.php`, `schema.sql`, `ui.html`, `tests/`, `data/`, `uploads/` закрыты в `.htaccess`
  (ветки и для Apache 2.4, и для 2.2, плюс `RewriteRule … [F]` как запасной вариант).
- Между таблицами нет внешних ключей (исторически, чтобы не зависеть от порядка миграций на хостинге);
  каскадные удаления делает код в транзакциях (`crm_delete_lead`, `delete_direction`, `purge_user`).
- В истории git до сентября 2026 лежали рабочий `config.php` и скриншоты — пароль MySQL из них нужно
  считать скомпрометированным и сменить в панели хостинга; при желании историю можно переписать
  (`git filter-repo`).
