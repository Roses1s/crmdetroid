# Полное код-ревью CRM «Детроид»

Дата: 2026-09-07. Ревью по состоянию ветки `arena/01a07d21-crmdetroid` (коммит `ed8abc9`).
Просмотрены все файлы: `api.php`, `db.php`, `js/app.js`, `js/theme.js`, `index.html`, `ui.html`,
`app.css`, `noscript.css`, `schema.sql`, `.htaccess` (все три), `config.example.php`, `tests/*`.

Шкала: 🔴 критично / 🟠 важно / 🟡 желательно / 🟢 заметка.

---

## 1. Общая оценка

Для «двух PHP-файлов без фреймворка» код **на удивление зрелый**. Видно, что проект прошёл
несколько итераций исправлений безопасности (комментарии в коде честно описывают старые
уязвимости и их фиксы): одноразовые login-токены с HMAC, bcrypt + dummy-hash против тайминг-атак,
лимиты входа по (email, IP) с учётом доверенных прокси, инвалидация сессий через
`token_version` + отпечаток пароля, проверка magic bytes у загрузок, оптимистическая блокировка
через `updated_at`, миграции под `GET_LOCK`. Это уровень выше среднего для самописных CRM.

Главные системные слабости — не отдельные баги, а **масштабируемость подхода**:
монолит из двух гигантских файлов, отсутствие FK в БД, полотно `innerHTML` на клиенте,
отсутствие CI и статического анализа. Плюс несколько конкретных дефектов ниже.

## 2. Найденные дефекты (конкретные)

### 2.1 🔴 `save_carrier`: любой сотрудник может редактировать чужого перевозчика — ✅ ИСПРАВЛЕНО
`api.php`, case `save_carrier` (~стр. 758–795). README и `save_direction` декларируют правило:
«переименовать направление **или перевозчика** может тот, кто его добавил, или админ».
`delete_carrier` проверяет `can_manage_ref()`, `save_direction` (rename) проверяет,
а ветка **обновления** в `save_carrier` — нет:

```php
$st = $pdo->prepare('SELECT * FROM crm_carriers WHERE id = ? AND direction_id = ?');
...
// нет can_manage_ref($user, $cur) !
$upd = $pdo->prepare('UPDATE crm_carriers SET name = ?, phone = ?, company = ?, note = ? ...');
```

Любой авторизованный сотрудник может переименовать/затереть карточку чужого перевозчика
(включая заметку). Это нарушение задокументированной модели прав.
**Фикс:** добавить `if (!can_manage_ref($user, $cur)) err('Переименовать перевозчика может тот, кто его добавил, или администратор');`
— либо явно задокументировать в README, что правка полей разрешена всем (но тогда
несимметрично с направлением).

### 2.2 🟠 `save_lead`: обращение к `$row['updated_at']` при `$row === null` + мёртвый `??` — ✅ ИСПРАВЛЕНО
`api.php:987`:

```php
$toName = crm_transfer_lead($pdo, $id, $uid, $toId, $ownerName, $stage, $via, (int) $row['updated_at'] ?? $now);
```

Две проблемы:
1. Приоритет операторов: `(int) $row['updated_at'] ?? $now` парсится как
   `((int) $row['updated_at']) ?? $now` — результат каста никогда не `null`, `?? $now` — мёртвый код.
2. При **создании нового лида с одновременной передачей** (`$row === null`) обращение
   `$row['updated_at']` из-под каста не попадает под null-подавление `??` → warning
   «Trying to access array offset on null» → ваш же `set_error_handler` превращает его
   в `ErrorException` → он не `PDOException` → пробрасывается → **500 вместо ответа**.
   Сейчас UI не создаёт лид с `transferTo` в одном запросе, поэтому баг латентный,
   но прямой вызов API его воспроизводит.

**Фикс:** `$row !== null ? (int) $row['updated_at'] : $now` (и вообще запретить transferTo
для только что созданного лида либо передавать `$now`).

### 2.3 🟠 Документация схемы разъехалась с кодом
`db.php`: `CRM_SCHEMA_VERSION = 13` и есть `crm_migrate_v13()` (индексы `idx_lead_time`,
`idx_carrier_time`, `idx_lead_created`). При этом:
- `schema.sql` в шапке: «schema version 12»;
- README: «Что делает текущая версия схемы (v12)».

Сам файл `schema.sql` индексы v13 содержит (т.е. отстала только шапка и README), но это
демонстрирует главный риск дублирования схемы: **`schema.sql` поддерживается руками** и
неизбежно дрейфует. **Фикс:** генерировать `schema.sql` скриптом из тестовой БД
(`mysqldump --no-data`) или хотя бы добавить проверку в тесты.

### 2.4 🟡 `logout` без CSRF-токена, если в сессии его ещё нет
`api.php`, ветка `logout`: `if ($have !== '' && ...) err('CSRF');` — при пустом
`$_SESSION['csrf']` проверка пропускается. Злоумышленник сторонним POST может разлогинить
пользователя (logout-CSRF). Риск низкий (DoS-неудобство), но проверку честнее сделать строгой.

### 2.5 🟡 Ошибки API всегда отдаются с HTTP 200
`out()/ok()/err()` не выставляют статус (кроме общего catch → 500 и пары мест в `file`).
`Нет прав` → 200, `Сессия истекла` → 200. Клиент завязан на `success:false`/`need_login`,
и это работает, но:
- ломается наблюдаемость: в логах хостинга/прокси всё выглядит как 200;
- сторонние инструменты (curl-мониторинг, fail2ban, uptime-чекеры) не видят проблем.

**Фикс:** `err()` принимает код (`err('Нет прав', 403)`), маппинг: 401 need_login, 403 права,
404 не найдено, 409 оптимистическая блокировка, 422 валидация, 429 лимиты.

### 2.6 🟡 `err('CSRF')` как сообщение о неверном методе
`if ($method !== 'POST' || !crm_want_json()) err('CSRF');` (login) и
`if ($method !== 'POST') err('Метод не поддерживается...')` рядом. Сообщение «CSRF» при
неправильном Content-Type дезориентирует при отладке интеграций.

### 2.7 🟡 Мусор в комментариях — след генерации
`js/app.js:147`: «Tab/Shift+Tab**循环** внутри открытой модалки» — китайские иероглифы
в русском комментарии. Мелочь, но стоит вычистить (поиск по не-ASCII вне строк).

### 2.8 🟡 Нет обработки коллизии id
Идентификаторы `l_/c_/a_/d_/k_ + bin2hex(random_bytes(6))` — 48 бит случайности.
Вероятность коллизии мизерная, но при её наступлении `INSERT` упадёт с duplicate key →
пользователь получит «Не удалось сохранить» без повтора. **Фикс:** один retry в цикле
или UUIDv7 (заодно сортируемость).

### 2.9 🟡 `loadActivity()` ходит мимо `Net.req`
`js/app.js`: вкладка «Активность» делает голый `fetch` — не обрабатывает `need_login`
(тихо ничего не покажет вместо выхода на форму логина), не показывает ошибки, не
переиспользует логику `as`. Плюс `_activityCache` растёт без ограничения (мелочь).

### 2.10 🟢 `crm_session_gc`: `@filemtime($f) < $limit` при ошибке
`filemtime` → `false` → `false < $limit` → `true` → попытка удалить файл, у которого не
прочиталось время. Практически безвредно (файл и так битый), но `(int)@filemtime(...) ?: PHP_INT_MAX`
было бы аккуратнее.

## 3. Безопасность (что уже хорошо и что усилить)

### Сделано хорошо ✅
- Login: одноразовые nonce-токены (HMAC + БД, TTL 15 мин), dummy-bcrypt против перечисления
  пользователей по таймингу, лимит 8/(email,IP) и 80/IP за 15 минут, «успех сбрасывает
  счётчик только своей пары (email, IP)».
- Сессии: `use_strict_mode`, HttpOnly, SameSite=Lax, Secure по `crm_is_https()`,
  regenerate_id на login/logout, свой каталог `data/sessions` (обход чужого GC на shared-хостинге),
  idle 8 ч + абсолютный срок 14 дней, отпечаток пароля + `token_version` → мгновенная
  инвалидация при смене пароля/роли.
- CSRF: заголовочный токен + `hash_equals`, GET-мутации запрещены, список read-only actions.
- Загрузки: белый список расширений + анти-двойное-расширение, magic bytes, случайное имя,
  каталог закрыт `.htaccess`, выдача только через `api.php?action=file` с проверкой прав
  и `realpath`-контейнментом, `nosniff`, RFC 5987 для кириллических имён.
- XSS: `esc()` применяется последовательно во всех `innerHTML`-шаблонах (проверял точечно
  все места конкатенации), `safeAttUrl()` — второй слой против `javascript:`-URL,
  CSP `script-src 'self'` без inline, плюс проверка «ui.html не содержит <script>».
- `X-Forwarded-For` доверяется только с явно перечисленных прокси, CIDR-парсер корректный
  (IPv4/IPv6, битовые маски).
- SQL: везде prepared statements; динамические имена таблиц проходят через белые списки
  (`crm_att_urls`, `crm_delete_att_rows`, `crm_insert_comment`).

### Стоит усилить 🔧
1. 🟠 **Права на редактирование перевозчика** — см. дефект 2.1.
2. 🟡 **Rate limit по IP на весь API.** Сейчас лимит 90/мин живёт в сессии — злоумышленник
   с валидной кукой ограничен, но каждая новая сессия = новый лимит; на `?action=file` — 600/мин
   на сессию. Для параноидального режима — счётчик по IP в `crm_login_attempts`-подобной таблице.
3. 🟡 **Заголовки**: добавить `Cross-Origin-Opener-Policy: same-origin`,
   `Cross-Origin-Resource-Policy: same-origin`; в HSTS рассмотреть `includeSubDomains`.
4. 🟡 **Argon2id** вместо `PASSWORD_DEFAULT` (bcrypt): `password_needs_rehash` при логине
   даст плавную миграцию. Bcrypt не плох, но 72-байтовый лимит уже заставил городить
   ограничение 64 символа.
5. 🟡 **Аудит-лог админских действий** (смена ролей, удаление сотрудников, sweep) — сейчас
   только error_log при сбоях. Таблица `crm_audit` дешёвая и сильно помогает при разборах.
6. 🟢 Ротация пароля БД: в комментарии признаётся, что «пароль БД однажды уже утёк в git».
   История репо squash-нута до 1 коммита — хорошо, но убедитесь, что пароль **сменён**, а не
   только скрыт.
7. 🟢 ZIP/7z принимаются без ограничений содержимого — для внутренней CRM приемлемо,
   но антивирус-скан (clamav на cron) не помешал бы.

## 4. Архитектура backend

1. 🟠 **Монолит из 2 файлов** (`api.php` 1343 стр. + `db.php` 1650 стр.). В коде уже есть
   отличный план рефакторинга (TODO #15, #18, #20 в шапках файлов) — его стоит наконец
   выполнить: `actions/*.php`, `http.php`, `security.php`, `files.php`, `migrations.php`.
   Сейчас `db.php` знает про HTTP (`out/err` с `header()`+`exit`) — слой данных не переиспользуем
   из CLI/cron, что сами авторы и признают.
2. 🟠 **`never`-функции (`err()`) внутри бизнес-логики** — поток управления через `exit`
   делает код нетестируемым юнитами: ни одну функцию из `api.php` нельзя вызвать в PHPUnit
   без буферизации вывода. Переход на исключения (`throw new ApiError(403, ...)`) + один
   обработчик — главный шаг к тестируемости.
3. 🟡 **Роутинг**: гигантский `switch` + цепочка `if ($action === ...)` до него. Таблица
   `['save_lead' => [handler, 'POST', 'csrf' => true, 'admin' => false]]` устранит дубли
   логики «read/write actions» и сделает права декларативными.
4. 🟡 **Дублирование лид/перевозчик**: `edit_comment` и `edit_carrier_comment`,
   `delete_comment` и `delete_carrier_comment`, `crm_lead_comments` и `crm_carrier_comments` —
   почти построчные копии (вставка уже обобщена в `crm_insert_comment`, TODO #19). Обобщить
   остальное параметром `kind`, как сделано в `delete_attachment`.
5. 🟡 **Смешение форматов ввода** (признано в TODO): `add_comment` — только FormData,
   `edit_comment` — JSON и FormData, остальное — JSON. Унифицировать.
6. 🟢 `applications_count` — денормализация с ручной синхронизацией (`crm_sync_lead_apps_count`).
   Работает, но триггер или полный отказ (COUNT на лету, есть индекс `idx_lead`) проще.

## 5. База данных

1. 🟠 **Нет FOREIGN KEY** — целостность держится на дисциплине кода + `integrity_check`
   (по сути ручной fsck). Все удаления каскадируются вручную в `crm_purge_*`. InnoDB уже
   используется, id-типы совместимы — FK с `ON DELETE CASCADE` для
   `comments→leads`, `attachments→comments`, `lead_apps→leads`, `carriers→directions`
   убрали бы целый класс багов и половину `crm_purge_*`. (Понимаю осознанность решения —
   на shared-хостинге FK иногда боятся, но MySQL 8 их отлично тянет.)
2. 🟠 **Этап лида хранится строкой-именем** (`crm_leads.stage VARCHAR(80)` ↔ `crm_stages.name`).
   Отсюда вся хрупкая механика `crm_stage_renames` («ровно один исчез и один появился — считаем
   переименованием»), `UPDATE ... NOT IN (...)` при сохранении этапов и потеря этапа при передаче
   лида. Ссылка `stage_id` на `crm_stages.id` устранила бы эвристику полностью.
3. 🟡 `save_stages` делает `DELETE всех этапов + INSERT заново` — id этапов не стабильны
   (сейчас на них никто не ссылается, но это блокирует п.2).
4. 🟡 Времена — `BIGINT` миллисекунды. Работает, но `DATETIME(3)` дал бы читаемость в
   phpMyAdmin и функции дат без `FROM_UNIXTIME(x/1000)` (см. п.6.3 про активность).
5. 🟢 Миграции: линейные, идемпотентные, под `GET_LOCK`, с честным комментарием про
   нетранзакционность DDL в v10 и сохранением сырых значений в `*_raw` — образцово для
   самописа. Единственное: `crm_run_migrations` прогоняет **все** миграции с нуля даже когда
   версия 12→13 (каждая сама проверяет "уже применено" через information_schema — это
   десятки лишних запросов на первый запрос после деплоя; терпимо, но версионный switch быстрее).

## 6. Производительность

1. 🟠 **Нет пагинации**: `get_data` отдаёт **все** лиды пользователя каждые 15–30 секунд
   каждой открытой вкладке. Хэш-механизм (`unchanged: true`) отлично экономит трафик при
   отсутствии изменений, но при любом изменении сериализуется вся доска. До ~1–2 тыс. лидов
   на пользователя — нормально; дальше нужны пагинация/дельты (`updated_since=<ts>`).
2. 🟡 **Поиск `LIKE '%...%'`** по title/inn — full scan (индексы не работают по ведущему `%`).
   Для роста: FULLTEXT-индекс по `title` + отдельное точное совпадение по нормализованному ИНН.
3. 🟡 `crm_client_activity`: `WHERE YEAR(FROM_UNIXTIME(a.created_at/1000)) = ?` —
   несаргируемое условие, full scan заявок. Заменить на диапазон:
   `a.created_at >= :jan1_ms AND a.created_at < :nextJan1_ms` — индекс `idx_lead_created`
   не поможет (нет user_id), но диапазон хотя бы отсечёт годы.
4. 🟡 **`.htaccess` не включает сжатие и кэширование статики**: нет `mod_deflate`/`mod_brotli`
   и `Expires`/`Cache-Control` для css/js. `app.css` (39 КБ) и `app.js` (~90 КБ) ходят
   несжатыми при каждом невалидированном запросе. Версионирование сейчас ручное (`?v=fix18` —
   легко забыть поднять). Добавить:
   ```apache
   <IfModule mod_deflate.c>
     AddOutputFilterByType DEFLATE text/css application/javascript text/html image/svg+xml
   </IfModule>
   <IfModule mod_expires.c>
     ExpiresActive On
     ExpiresByType text/css "access plus 1 year"
     ExpiresByType application/javascript "access plus 1 year"
   </IfModule>
   ```
   (при годовом кэше `?v=` должен меняться при каждом деплое — лучше hash в имени файла).
5. 🟢 На каждый запрос — `SELECT v FROM crm_meta WHERE k='schema'` (crm_boot). Дешево, ок.
6. 🟢 Подзапросы-COUNT в списках направлений/перевозчиков — N+1 внутри одного SQL, для
   справочника это нормально.

## 7. Frontend (js/app.js, ui.html, app.css)

### Хорошо ✅
- Дисциплина `esc()` во всех шаблонах, делегирование событий через `data-action`,
  оптимистическая блокировка с `_editRev`, цепочки сохранений (`_leadSaveChain`) против
  гонок автосейва, adaptive polling (15с → 30с при простое), `keepalive` в `beforeunload`,
  focus-trap и aria-атрибуты в модалках, защита от автозаполнения пароля в таблице
  сотрудников (детект ручного ввода) — редкая внимательность.

### Слабые места 🔧
1. 🟠 **2291 строка в одном файле без модулей.** `Store`, `Net`, `UI`, роутер, канбан,
   формы, файлы, активность — всё в глобальной области. Даже без сборщика можно перейти на
   нативные ES-модули (`<script type="module">`): `net.js`, `store.js`, `board.js`,
   `lead.js`, `routes.js`, `users.js`, `activity.js`. Это же уберёт хак
   в e2e-тесте, который дописывает `window.Store=Store...` к исходнику.
2. 🟠 **Рендер через innerHTML-полотна.** Помимо читаемости, это причина потери состояния
   (весь лог перерисовывается при каждом изменении, редактор восстанавливается вручную
   через `UI.editingCommentId`). Минимальный шаг — `<template>`-элементы в ui.html вместо
   строковых шаблонов; максимальный — лёгкая библиотека (lit-html/preact, ~4–10 КБ) без
   изменения бэкенда.
3. 🟡 **Глобальный флаг `UI.formDirty` один на все формы** (лид и перевозчик различаются
   только по `UI.carrierId`) — уже сейчас в `switchView/openRoute/openCarrier` по 6 строк
   «сохрани то, потом это». Состояние «что редактируем» просится в объект.
4. 🟡 `withLock` глушит параллельные клики глобально — при зависшем запросе (нет таймаута
   у `fetch`!) интерфейс молча перестаёт реагировать на действия. Добавить
   `AbortSignal.timeout(15000)` в `Net.req` и сброс лока.
5. 🟡 Дубли plural-функций: `plural()`, `carrierWord()`, `appsWord()` — три реализации
   одного склонения. Оставить `plural(n, ...)`.
6. 🟡 `handleLogoutUI` не вызывается для не-JSON 401 везде (обрабатывается), но
   `loadActivity` — мимо (см. 2.9).
7. 🟢 Телефонная маска жёстко заточена под +7/8 — для международных перевозок может мешать
   (маска пропускает `+` не-РФ, но UX спорный).
8. 🟢 A11y: drag-n-drop канбана недоступен с клавиатуры (перенос этапа возможен только
   мышью; карточку можно двигать кнопками этапов в карточке — уже неплохо). Тостам не хватает
   `role="status"`/`aria-live`.
9. 🟢 Мобильность: `body { overflow: hidden }` + 4 media-query — планшет ок, телефон
   «терпимо». Если менеджеры работают с телефона, нужен отдельный проход по UX.

## 8. Тесты и CI

1. 🟠 **Нет CI.** Оба набора тестов (57 проверок в `api-smoke.sh`, ~15 в `e2e-jsdom.mjs`)
   запускаются руками против живого стенда. GitHub Actions с `services: mysql:8` +
   `shivammathur/setup-php` запустит их на каждый push бесплатно — это самое дешёвое
   улучшение с максимальной отдачей.
2. 🟠 **Нет юнит-тестов чистых функций**, а их много и они идеальные кандидаты:
   `crm_parse_money`, `crm_legacy_money`, `crm_money_out`, `crm_ip_in_list`, `crm_client_ip`,
   `crm_stage_renames`, `crm_upload_name`, `crm_short_filename`, `crm_like_pat`. PHPUnit +
   таблично-управляемые кейсы. Сейчас парсер денег — самая рискованная логика (миграция v10
   уже ловила «12 500,50 → 1250050») и она не покрыта ничем, кроме двух smoke-проверок.
3. 🟡 Smoke-тесты пишут в общую БД стенда и полагаются на заранее созданных
   пользователей (`ivan@x.ru`, «Пётр Сидоров» для e2e) — сделать сетап самодостаточным
   (e2e сам создаёт своих пользователей через API админа, как это делает smoke).
4. 🟡 Статический анализ отсутствует: PHPStan (level 6+ пройдёт почти сразу — типы уже
   расставлены), ESLint + Prettier для js. PHPStan поймал бы дефект 2.2 автоматически
   (`Offset 'updated_at' does not exist on null`).

## 9. Процессы и репозиторий

1. 🟡 История squash-нута до одного коммита «Delete uploads/1» — история изменений и
   авторство утрачены; дальше стоит вести нормальные атомарные коммиты.
2. 🟡 Нет `composer.json` (даже пустого с `"require": {"php": ">=8.1"}` и scripts для
   тестов/линтеров) и `package.json` — инструментам не за что зацепиться.
3. 🟡 Деплой — ручная заливка файлов по списку из README («не перезаписывайте config.php,
   uploads/, data/»). Одна ошибка — потеря вложений. Минимум: rsync-скрипт с `--exclude`,
   лучше — деплой по git + симлинки на shared-каталоги.
4. 🟡 Бэкапы: README требует «перед обновлением снимите дамп руками». Cron с
   `mysqldump | gzip` + ротация (на SpaceWeb cron есть) — час работы.
5. 🟢 `.gitignore`, `.htaccess`-защиты, `robots.txt` — образцово.
6. 🟢 Нет LICENSE — для внутреннего проекта ок, но стоит зафиксировать намеренно.

## 11. Резюме

Проект в хорошей форме для своего класса: продуманная безопасность, честные комментарии,
рабочие тесты, аккуратные миграции. Два реальных дефекта требуют немедленного фикса
(права на перевозчика и null-обращение в save_lead), остальное — планомерная работа по
инфраструктуре качества (CI, статанализ, юнит-тесты) и постепенный распил монолитов,
план которого авторы уже сами записали в TODO. Самый большой стратегический риск — не код,
а процессы: ручной деплой, ручные бэкапы и отсутствие автоматических проверок.
