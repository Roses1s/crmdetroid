# Анализ кода: CRM «Детроид» (`crm.html`)

## 1. Что это за проект

Однофайловое клиентское веб-приложение (чистые HTML + CSS + vanilla JS, без сборки и бэкенда) —
мини-CRM для ведения лидов в формате канбан-доски. Судя по полям («Что возят?», «Формат перевозки»,
«Тип клиента (АТИ)»), сделана под логистическую компанию ООО «Детроид». Интерфейс явно вдохновлён
Odoo CRM (фирменный фиолетовый #714B67, «chatter»-лог справа от карточки).

## 2. Архитектура

| Слой | Реализация |
|---|---|
| Хранение | `localStorage`, ключ `crm_leads_v8` (версионированный — итераций было много) |
| Состояние | Глобальный массив `leads` + `currentLeadId`, `editingCommentId`, `pendingAttachments` |
| Рендеринг | Императивный: `innerHTML` + `createElement`, без фреймворков |
| Представления | Два экрана в одном HTML: `#kanban-view` и `#detail-view` (переключение через `display`) + модалка создания |

Модель данных лида: `id, title, stage, manager, inn, phone, email, cargo, format, payment, ati, tag,
applicationsCount, comments[]` (комментарий: `id, text, author, time, attachments[]`, где вложения —
base64 data-URL целиком в localStorage).

## 3. Функциональность

- Канбан из 6 стадий воронки («Новый» … «Уехали, ждем заявку») со счётчиками карточек.
- Drag-and-drop карточек между стадиями + автозапись смены статуса в лог.
- Создание лида через модалку (название обязательно, ИНН/телефон/email опциональны).
- Детальная карточка: инлайн-редактирование полей с автосохранением по `onchange`,
  кнопки стадий, кнопка «Сохранить», удаление карточки через меню-«шестерёнку».
- Лог-«чаттер»: комментарии (Enter — отправить, Shift+Enter — перенос), инлайн-редактирование
  и удаление комментариев, вложение файлов (в т.ч. превью изображений и скачивание).
- Счётчик «Заявки» в шапке лог-панели.
- При первом запуске — демо-данные (один лид).

## 4. Сильные стороны

- Аккуратный, цельный и читаемый код для прототипа; логика компактная и понятная.
- `escapeHtml()` применяется к тексту комментариев и именам вложений — основной XSS-вектор закрыт.
- Аудит-лог: смена стадии (и drag-and-drop, и кнопками) фиксируется системным комментарием.
- Продуманные мелочи: `e.isComposing` в обработчике Enter (для IME), автоскролл/фокус
  в инлайн-редакторе, сброс `input.value` после выбора файлов, обратный порядок лога (новые сверху).

## 5. Баги и риски (по приоритету)

### Высокий
1. **Падение при битом хранилище.** `JSON.parse(localStorage.getItem('crm_leads_v8'))` на верхнем
   уровне скрипта без `try/catch`: любое невалидное значение в ключе — и приложение не стартует вообще.
2. **Потеря данных при переполнении хранилища.** Вложения хранятся как base64 в `localStorage`
   (лимит ~5 МБ на домен, +33% к размеру от base64). `saveDb()` без `try/catch` —
   `QuotaExceededError` при большом файле оставляет состояние несогласованным, пользователь
   не получает никакой ошибки.
3. **Незакрытый XSS.** В `renderBoard()` в `innerHTML` карточки подставляются `lead.title`,
   `lead.tag`, `lead.phone`, `lead.manager` **без** `escapeHtml()`. Название компании вида
   `<img src=x onerror=...>` выполнится как код. В комментариях всё экранировано, в канбане — нет.

### Средний
4. **Хрупкая система ID.** У сид-лида `id: 1` (число), у новых — `Date.now()`. В drag-and-drop
   сравнение нестрогое (`l.id == id`, строка из `dataTransfer`), а в удалении — строгое
   (`l.id !== currentLeadId`). Пока работает, но любое изменение источника `id` это сломает.
   То же с `id` комментариев: два действия в одну миллисекунду = коллизия; патч
   `if (!c.id) c.id = Date.now() + idx` тоже может столкнуться с существующими.
5. **Лиды «вне воронки» исчезают.** Доска рендерит только стадии из `STAGES`; если в хранилище
   окажется лид с другим/старым значением `stage` (ключ уже версионировался 8 раз), он пропадёт
   из UI безвозвратно для пользователя. Нужна колонка-фолбэк или нормализация при загрузке.
6. **«Изменения сохранены!»** показывается alert-ом даже если ничего не менялось
   (`saveLeadDetails(true)` не проверяет `isChanged`).

### Низкий
7. `history.innerHTML += ...` в цикле — пересборка всего уже отрендеренного на каждой итерации
   (O(n²), повторная загрузка картинок). На больших логах лучше `DocumentFragment`.
8. Модалка создания не закрывается по клику на подложку и по `Escape`.
9. `min="0"` у счётчика заявок — только атрибут, в коде отрицательные значения не отсекаются.
10. Нет валидации ИНН/телефона/emails (только плейсхолдеры).
11. Редактирование комментария затирает исходное время (`время + " (изм.)"`), история правок теряется.

## 6. Безопасность и данные

- Бэкенда и авторизации нет: это локальный инструмент одного браузера. «Пользователь» в логе
  захардкожен, мультипользовательской работы и синхронизации нет в принципе — это ограничение
  архитектуры, а не баг.
- В демо-данных захардкожены реквизиты и контакты реального предприятия (название, ИНН,
  телефон, email). Для публичного репозитория их стоит заменить на вымышленные.
- Данные пользователя в `localStorage` не шифруются и доступны любому скрипту страницы —
  при появлении внешних скриптов/расширений это надо учитывать.

## 7. UX / адаптивность

- Колонки фиксированные 260px, форма в 2 грида без медиа-запросов, `body { overflow: hidden }` —
  на мобильных будет тесно и с горизонтальным скроллом.
- Кликабельные `<div>`/`<strong>` вместо кнопок, нет aria-атрибутов, перетаскивание недоступно
  с клавиатуры — доступность формально не обеспечена.
- Нет поиска/фильтра по лидам, нет сумм по колонкам (если появятся деньги в модели).

## 8. Рекомендации

**Быстрые исправления (1–2 часа):**
- Обернуть `JSON.parse` и `saveDb` в `try/catch` (с алертом об ошибке квоты).
- Прогнать все пользовательские поля через `escapeHtml()` в `renderBoard()`.
- Закрытие модалки по `Escape`/клику на оверлей.

**Среднесрочные:**
- `crypto.randomUUID()` для всех ID; нормализация неизвестных `stage` при загрузке.
- Вложения — в IndexedDB (сотни МБ вместо 5), в `localStorage` только метаданные;
  ограничение размера файла с предупреждением.
- Экспорт/импорт данных (JSON/CSV) — сейчас бэкапа нет вообще.

**Если проект будет расти:**
- Разнести CSS/JS по файлам, выделить слой хранилища (репозиторий) и рендеринга.
- Для нескольких менеджеров потребуется бэкенд (хотя бы простой REST + БД) и авторизация;
  текущая модель `localStorage` это не переживёт — проще переписать слой данных, чем чинить.

## Итог

Качественный рабочий прототип «для себя»: чистая логика, продуманный UX воронки и лога.
Главные технические долги — отсутствие обработки ошибок хранилища (риск полной потери данных),
один незакрытый XSS в карточках канбана и потолок `localStorage` для вложений.
Для личного использования достаточно закрыть пункты из «быстрых исправлений»;
для командной эксплуатации нужен переход на серверное хранение.
